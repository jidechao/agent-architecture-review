# Agent 工程架构设计审查 Skill

一个用于审查**第三方 AI Agent / 智能体 / Copilot / Agent 平台**工程设计合理性的 Claude Code Skill：把产品材料与可观察行为转化为**有证据、可复核、能指导整改**的中文审查报告。

审查的重点不是模型是否"聪明"，而是：**模型的判断能否通过运行时转化为可靠、可控、可恢复、可追踪的实际行动。**

> 本 Skill 的审查基线蒸馏自文章[《AI Agent 的核心架构到底是什么？从 ReAct 到状态机，一次讲透》](https://mp.weixin.qq.com/s/RdbmbNs1qCo2O6FyFZMBeQ)，并将其运行时思想（五要素、五道防线、错误三分类、状态机、Checkpoint/幂等、事件流等）转化为可操作的审查问题。业务中立：销售、研发、运维、医疗、办公或其他领域只改变任务风险和证据来源，不改变审查方法。

## 它解决什么问题

评测一个 Agent 产品时，最常见的三个失败模式：

1. **只看答案外观**——"回答得很流畅"不等于真实查询过工具、不等于没有编造成功、不等于失败时有确定行为；
2. **被宣传语与状态名称误导**——UI 显示"已取消"不代表外部动作未发生，文档声明"支持重试"不代表故障时有效；
3. **发现无法指导整改**——"加强安全""提升鲁棒性"式的意见不能转化为可复测的验收标准。

本 Skill 用一套确定的审查方法替代凭感觉的评审：**先判断任务与动作风险，再按九个维度取证评分，用故障注入验证关键结论，最后输出带证据链、严重度、门禁判定与改进路线的报告。**

## 核心判断原则

审查全程贯穿七条原则（源自运行时架构思想，与具体框架无关）：

1. **架构随任务复杂度走**：单次模型调用、Workflow、Agent 和混合架构各有适用场景，固定路径不需要为了"智能化"交给模型；
2. **模型提出意图，程序负责验证和执行**：工具调用、计划、审批建议和参数修正都不是已执行事实；
3. **Agent 是运行时，而非 LLM + Tools**：至少还原 LLM、Tools、State、Loop、Stop 五部分职责及其交互；
4. **可靠不是从不出错，而是错误时有确定行为**：有边界地重试、修正、降级、停止、恢复，并保留记录；
5. **证据不足不等于实现缺失**：分别记录已证实事实、合理推断和未决问题（NE），不用宣传语代替证据；
6. **高风险动作需要确定性边界**：权限、审批、业务规则、幂等、事务和审计不能只靠 Prompt；
7. **最终答案正确不代表执行成功**：同时检查工具结果、中间状态、外部副作用和答案证据链。

## 九维审查基线

| 维度 | 权重 | 审查要点 |
|---|---:|---|
| D1 架构适配与确定性边界 | 10 | 路径复杂度与架构是否匹配；哪些环节允许模型动态决策；动作风险分级（只读/可逆/不可逆） |
| D2 执行循环与状态机 | 10 | Think→Act→Observe 闭环；调用 ID 关联；非法响应处理；状态语义与终态守卫；Recovering 与 Failed 终态区分；终态后能否被迟到事件"复活" |
| D3 状态、上下文与持久化 | 10 | 状态是否超越聊天记录；裁剪/摘要/重读是否保留关键事实；Checkpoint 原子性与并发；统一存储接口抽象 |
| D4 工具治理、权限与副作用 | 15 | 注册表拒绝未知/重名工具与静默降级；扩展面缺省安全值与授权粒度；执行前校验；审批绑定要素（主体/工具/资源/参数/有效期）；未知结果的核对与补偿；eval/代码类输入的资源边界 |
| D5 停止、预算、超时与取消 | 12 | 步数/实际 Token 与费用/三层超时/无进展检测/自愈上限共同有效；取消四层语义（停止调度→拦截写入→尽力取消→核对真实副作用） |
| D6 错误处理、自愈与恢复 | 15 | 错误三分类（参数/瞬时/不可恢复）+ 结果未知；退避与抖动；自愈后重新校验；Checkpoint 恢复先核对未决外部动作；部分失败不伪造成完整成功 |
| D7 规划、依赖与并行控制 | 6 | 是否真的需要规划/并行；模型提计划、程序验计划（依赖存在性/环/工具许可/预算）；环境变化重规划；多智能体按能力启用检查（预算共享、取消传播、最小权限、递归深度） |
| D8 可观测性、审计与证据链 | 10 | 结构化事件与流式增量；统一异步接口与 UI 解耦；Trace 六问；执行状态与结果状态区分；与独立事实源对账；不依赖隐藏思维链 |
| D9 测试、评估与发布保障 | 12 | 模拟模型/工具的离线测试 + 真实集成评估；答案与中间过程同时断言；故障路径覆盖（取消/恢复/审批绕过/终态后调用/重复副作用）；多次运行的统计门槛 |

每个维度在 `references/review-rubric.md` 中展开为具体的审查问题、正向证据与典型缺陷。

## 评分体系

每个维度按**已被证据证明的设计或行为**评分（宣传材料中的能力名称不算）：

| 评分 | 含义 |
|---:|---|
| 0 | 已证实关键机制缺失，或当前设计会直接导致严重风险 |
| 1 | 有局部实现，但主要依赖 Prompt、人工经验或临时逻辑 |
| 2 | 核心机制基本完整，边界或异常路径仍有明显缺口 |
| 3 | 关键路径有确定性控制和较完整验证，少量非阻断缺口 |
| 4 | 正常与故障路径均经充分验证，能持续度量与回归 |
| NE | 证据不足，无法评分——NE ≠ 0，也不代表机制不存在 |
| NA | 与当前任务确实无关——必须写明理由，不能用来回避不利审查 |

```text
已覆盖维度加权分 = 100 × Σ(适用且已评分维度的权重 × 评分 / 4) ÷ Σ(适用且已评分维度的权重)
证据覆盖率     = Σ(适用且已评分维度的权重) ÷ Σ(全部适用维度的权重) × 100%
```

公式设有**反陷阱条款**：只覆盖 60% 权重且这些维度全是 4 分时数字会是 100——因此高风险动作的关键控制（授权审批、幂等与恢复、结果真实性）仍为 NE 时，不展示该数字；分数用于汇总，不代替判断。

## 发布门禁与结论决策

六类已证实问题触发门禁，**不能被其他维度的高分抵消**：

1. 高风险写入只依靠 Prompt 或模型自律完成授权、审批与业务校验；
2. 对结果未知或不可逆动作盲目重试，且没有幂等、状态核对或补偿机制；
3. 执行循环、错误自愈或外部调用没有实际上限，可能持续消耗资源；
4. 崩溃恢复可能重放未确认的高风险动作，造成重复副作用；
5. 系统把工具失败或结果未知包装成确定成功，且该结果会驱动重要决策；
6. 敏感信息以不可接受的方式暴露，或高风险操作无法审计。

> **门禁 1 的授权来源判据**（2026-10 实践补丁）：用户显式配置扩展点（如自带凭证接入某工具服务）构成粗粒度用户授权，不等于"只靠模型自律"；但"缺省全量暴露 + 无按工具授权粒度 + 写类工具无独立确认路径"的组合应记为高风险未整改项（结论上限"有条件通过"）。产品自带的写能力若无任何执行层授权，才直接构成门禁 1。

| 证据与门禁状态 | 允许的最高结论 |
|---|---|
| 无已证实门禁问题；覆盖率 ≥ 80%；高风险路径有行为证据 | 通过 |
| 无阻断级门禁，但存在高风险未整改项，或覆盖率 60%–80% | 有条件通过（须写明限制场景与复测期限） |
| 门禁清单 1–6 中任一项已证实 | 不通过（不可被高分抵消） |
| 覆盖率 < 60%，或高风险关键控制仍为 NE | 证据不足，暂不评级（不并合单一总分） |

## 故障注入矩阵

`references/fault-injection.md` 提供 22 个行业无关的测试场景，按能力选择执行，不要求机械跑完：

- **核心 17 项**（T-01~T-17）：基线与直接回答、非法模型响应、参数错误与自愈上限、瞬时错误、不可恢复错误、分层超时、重复无进展（含绕过简单签名的形态与合理轮询对照）、步数与资源预算、取消语义（含取消与写入并发、迟到结果）、审批与权限绕过（含实质变更使旧审批失效）、外部结果未知、崩溃恢复（执行前/执行后保存前两个崩溃点）、部分失败与信息不足、长上下文与摘要、Trace 与停止诊断、重复与随机性评估；
- **按能力追加 5 项**（T-18~T-22）：规划计划校验、环境变化重规划、并行执行、多实例与长任务、异步工具与事件乱序。

矩阵同时定义安全前提（只用模拟模型/沙箱/虚拟业务对象，不真实付款下单）、四档证据模式（黑盒/灰盒/白盒 + **零成本故障探针**）、以及五种结果判定（通过/失败/无法判断/未执行/不适用）——**未执行绝不写成通过**。

## 证据表述规范

报告强制区分事实与推断，防止"看起来专业"的猜测混入结论：

| 情况 | 表述示例 |
|---|---|
| 已观察/已验证 | "测试 T-02 中，取消后仍发生了一次工具调用（E-04）。" |
| 基于证据的推断 | "该行为表明 UI 取消未阻止后续调度；底层请求是否仍运行尚无法确认。" |
| 未提供证据 | "未获得状态转换实现证据，本项记为 NE，而非认定不存在状态机。" |
| 供应商声明 | "设计文档声明支持有限重试，尚需用超时与错误分类测试验证。" |
| 不适用 | "产品无规划与并行执行，且当前任务不需要，D7 记为 NA。" |

## 审查流程

```text
1. 确定范围与证据模式   → 产品/版本/任务/风险分级；黑盒|灰盒|白盒可组合；建立 E-编号证据清单
2. 还原运行时与信任边界 → Think→Act→Observe 控制流；五要素；状态/终态/审批/取消路径；数据流
3. 架构适配 + 静态审查   → 先判断复杂度匹配，再按九维评分（0–4/NE/NA + 证据 + 置信度）
4. 故障验证关键结论     → 按风险选择 T-xx 场景；未执行如实标注；绝不为验证幂等真实重复付款
5. 形成发现与建议       → 证据→缺口→触发条件→后果→改进机制→验收方法 的完整因果链
6. 评分、覆盖率与门禁   → 严格套用公式与决策表；门禁不可被高分抵消
7. 输出审查报告         → 快速档 / 完整档两档深度，均不得省略证据边界与最高风险
```

## 报告交付

- **快速档**：单一关注点、材料很少时——结论 + 证据边界 + 该侧面关键发现；未覆盖维度明确列 NE；
- **完整档**（默认）：9 节结构——执行摘要与发布建议 / 证据清单与限制 / 架构还原与风险边界 / 评分覆盖率门禁 / 详细发现（每条含证据、失败场景、根因、改进建议、可复测验收标准、置信度）/ 故障测试结果 / P0-P2 改进路线 / 复测退出条件 / 最终意见。

模板见 `references/report-template.md`。

## 适用与不适用

**适用**：

- 采购/验收前的第三方 Agent 产品评估（黑盒试用记录 → 报告）；
- 接入前的设计方案评审（设计稿/接口文档 → 灰盒审查）；
- 自研或开源 Agent 项目的上线前工程审查（源码+测试+运行工件 → 白盒审查）；
- 为 Agent 产品设计验收测试清单、故障注入方案或取证方案。

**不适用**：

- 纯概念解释（"什么是 ReAct"）；
- 从零实现一个 Agent 的编码请求；
- 与运行时工程严谨性无关的纯模型能力评测（如答题准确率榜）。

## 使用方式

安装后直接用自然语言发起，Skill 会自动触发：

```text
# 黑盒：基于试用记录审查 SaaS 产品
我们准备采购附件里的 XX Copilot。请基于试用记录做一次第三方 Agent 工程架构审查，
重点判断结果可信度与容错性，并给出采购建议。

# 灰盒：设计稿评审
这是我们准备接入财务系统的 XX Agent 设计稿。请从工程设计合理性、严谨性、
容错和副作用安全角度审查，输出问题清单和改进建议。

# 白盒：源码审查（如开源 Agent 项目）
请对 <仓库路径> 的 main 分支做一次完整的工程架构审查，评估能否用于生产。
```

也可以显式调用：`/agent-architecture-review`（若运行时支持按名调用）。

报告默认输出中文 Markdown；可指定其他语言或输出为文件。

## 评测与验证

本 Skill 按对照测试方法开发（相同任务、有/无 Skill 各跑一遍、独立评分断言）：

| 轮次 | 技能版 | 基线版（无 Skill） | 结论 |
|---|---|---|---|
| 第 1 轮（3 场景 × 26 断言） | 26 / 26 | 23 / 26 | 技能版全过；修订点（取消/预算不可重试、自愈上限、NE/门禁纪律）在重跑中验证生效 |
| 第 2 轮（同套断言独立复跑） | 26 / 26 | 21 / 26（80.8%） | 独立对抗复核的 9 项发现全部落实并验证 |

评测覆盖三种证据条件：黑盒采购试用（`evals/fixtures/sales-copilot-blackbox.md`）、高风险设计稿（`payment-agent-design.md`）、成熟混合架构正面案例（`incident-review-hybrid.md`）。评测定义见 `evals/evals.json`。

**实践记录**：2026-10-17 对一个真实开源 Agent 项目（Plan-Execute/ReAct 混合调研智能体）完成首次白盒实践审查——九维覆盖率 100%，零成本故障探针现场证实"未知工具名静默降级"缺陷；该实践反哺了门禁 1 授权来源判据、D4 扩展面缺省安全值两条基线补丁与"零成本探针/历史运行产物"取证方法。

## 局限性

- 审查结论受证据模式约束：黑盒下内部机制只能标 NE，不能替代白盒取证；
- 评分权重面向"会执行外部动作的通用 Agent"校准；纯对话类产品的 D4/D5 部分检查会自然落为 NA；
- 22 项故障矩阵是风险驱动的选择集，不是穷举——特定行业（金融结算、医疗、基础设施变更）应在此基础上叠加行业合规检查；
- 评测断言当前为中文报告定制；其他语言输出需自行校准断言措辞。
