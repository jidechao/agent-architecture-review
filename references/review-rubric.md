# Agent 工程架构审查基线

本基线将《AI Agent 的核心架构到底是什么？从 ReAct 到状态机，一次讲透》中的运行时思想转化为审查问题。原文链接：https://mp.weixin.qq.com/s/RdbmbNs1qCo2O6FyFZMBeQ

适用于任何行业和任意 Agent 产品，不预设具体业务流程。先判断任务与动作风险，再选择适用检查项；不要因为某个产品没有采用自己喜欢的框架、状态库或规划算法而扣分。

## 1. 评分、证据与结论规则

### 1.1 维度评分

每个维度使用以下评分，评分对象是**已被证据证明的设计或行为**，不是宣传材料中的能力名称。

| 评分 | 含义 |
|---:|---|
| 0 | 已证实关键机制缺失，或当前设计会直接导致严重风险 |
| 1 | 有局部实现，但主要依赖 Prompt、人工经验或临时逻辑，缺少一致约束 |
| 2 | 核心机制基本完整，但边界、异常路径或验证证据仍有明显缺口 |
| 3 | 关键路径有确定性控制和较完整验证，仅存在少量非阻断缺口 |
| 4 | 设计与实现证据一致，正常和故障路径均经充分验证，并能持续度量与回归 |

- **NE（Not Evidenced）**：证据不足，无法评分。NE 不等于 0，也不代表机制不存在。
- **NA（Not Applicable）**：该维度与当前任务确实无关。必须写清理由，例如未使用规划且任务无需规划；不能用 NA 回避不利审查。

数字分数命名为**已覆盖维度加权分**，它只汇总已评分维度，不能当作产品整体结论：

```text
已覆盖维度加权分 = 100 × Σ(适用且已评分维度的权重 × 评分 / 4) ÷ Σ(适用且已评分维度的权重)
证据覆盖率 = Σ(适用且已评分维度的权重) ÷ Σ(全部适用维度的权重) × 100%
```

注意该公式的陷阱：只覆盖 60% 权重且这些维度均为 4 分时，数字会是 100。因此高风险动作的关键控制（授权审批、幂等与恢复、结果真实性）仍为 NE 时，**不展示该数字**，避免其他维度的已知高分掩盖关键未知项。同一维度内部也应区分关键控制与次要子项：关键控制未知时，该维度不应仅凭次要子项给高分。

### 1.2 证据与置信度

- **强证据**：可复现测试、实际 Trace/日志、与运行版本一致的代码和配置、外部系统操作记录。
- **中等证据**：详细设计文档、接口契约、供应商演示；能说明设计意图，但不能单独证明线上行为。
- **弱证据**：宣传语、能力标签、UI 上的状态名称、无法核实的口头说明。

分别记录“事实”“基于事实的推断”“待验证问题”。代码存在不等于运行时已启用；文档声明不等于故障时有效；一次成功演示不等于稳定能力。

### 1.3 严重度与发布门禁

| 严重度 | 判定参考 |
|---|---|
| 阻断 | 可能造成未授权或重复的高风险副作用、严重数据/安全问题，或核心结果系统性失真且会直接影响重要决策 |
| 高 | 很可能导致任务失控、重复业务操作、恢复失败、不可接受成本，或关键故障无法诊断 |
| 中 | 局部可靠性、成本、兼容性或可维护性不足，有变通方式但应优先改进 |
| 低 | 不直接影响正确性和安全性的优化项 |

以下已证实问题通常触发门禁，不能被其他维度的高分抵消：

1. 高风险写入只依靠 Prompt 或模型自律完成授权、审批与业务校验。
2. 对结果未知或不可逆动作盲目重试，且没有幂等、状态核对或补偿机制。
3. 执行循环、错误自愈或外部调用没有实际上限，可能持续消耗资源。
4. 崩溃恢复可能重放未确认的高风险动作，造成重复副作用。
5. 系统把工具失败或结果未知包装成确定成功，且该结果会驱动重要动作或决策。
6. 敏感信息以不可接受的方式暴露，或高风险操作无法审计。

判定门禁 1 时区分**授权来源与授权粒度**：用户显式配置扩展点（如自带凭证接入某个工具服务）构成对该扩展点的粗粒度用户授权，不等于"只靠模型自律"；但"缺省全量暴露 + 无按工具的授权粒度 + 写类工具无独立确认路径"的组合，应记为高风险未整改项（结论上限"有条件通过"），并要求扩展面收紧后复测。产品自带的写能力若无任何执行层授权与审批，才直接构成门禁 1。

总体结论按以下决策表确定，同一证据下只允许一个结论；拿不准时取更保守的一档：

| 证据与门禁状态 | 允许的最高结论 | 附加要求 |
|---|---|---|
| 无已证实门禁问题；覆盖率 ≥ 80%；高风险动作与关键故障路径有行为证据 | 通过 | 列出剩余 P1/P2 项与复测建议 |
| 无已证实**阻断级**门禁，但存在高风险未整改项，或覆盖率 60%–80% | 有条件通过 | 必须写明限制的适用场景、风险隔离措施与复测期限；不得默认全场景放行 |
| 门禁清单 1–6 中任一项**已证实** | 不通过 | 结论不可被其他维度高分抵消；即使已覆盖维度加权分为高分 |
| 覆盖率 < 60%，或高风险动作的关键控制（授权审批、幂等与恢复、结果真实性）仍为 NE | 证据不足，暂不评级 | 不展示已覆盖维度加权分之外的产品级分数；列出取证与复测前提 |

“暂不评级”时可以展示已覆盖维度的分项评分供参考，但必须与产品级结论明确区分标注，不得并合成单一总分。

## 2. D1：架构适配与确定性边界（权重 10）

### 审查问题

- 任务执行路径是预先固定、半固定，还是必须根据运行时结果动态决定？单次模型调用、Workflow、Agent 或混合架构是否与这种复杂度匹配？
- 哪些环节允许模型动态决策，哪些环节必须由确定性程序控制？
- 模型、工具、状态、循环和停止控制的职责是否清晰？模型输出是否仅被视为行动意图，而非已发生的事实？
- 架构复杂度是否由业务风险与任务复杂度驱动，而不是为使用 Agent、DAG、多智能体或框架而引入？
- 是否对工具动作按只读、可逆写入、高风险或不可逆写入分级？

### 正向证据

- 有任务路径与动作风险分析；稳定流程采用 Workflow，动态判断环节才嵌入 Agent。
- 权限、审批、事务、入账或其他关键业务约束位于确定性执行层。
- 决策、执行、状态保存和终止职责可以独立定位、测试和替换。

### 典型缺陷与改进方向

- **固定路径全部交给模型**：将稳定环节改为 Workflow，仅在真正需要动态判断的位置使用 Agent。
- **Prompt 充当执行边界**：把约束下沉到运行时和工具执行层。
- **巨型函数混合所有职责**：按决策、执行、状态、预算、事件和存储拆分；小型 Demo 不必过度拆分。

## 3. D2：执行循环与状态机（权重 10）

### 审查问题

- 是否形成完整的 Think → Act → Observe 闭环：模型决策、程序执行、真实结果回填、状态更新、再次决策？
- 工具调用与结果是否通过调用 ID 等稳定标识关联？乱序、重复或缺失结果如何处理？
- 模型返回未知响应、非法工具名、损坏 JSON 或不符合协议的调用时，运行时会怎样？
- 是否定义有清晰语义的状态及合法转换，而不仅是几个状态字符串？终态是否阻止继续调度？
- 长任务是否需要 WaitingApproval、Paused、Cancelled、WaitingTool 等状态；每种状态是否有明确进入条件、退出条件和守卫？
- 错误态是否区分**可恢复**（Recovering：自愈、重试、重新规划期间的中间态，受预算与次数约束）与**终态失败**（Failed：无进一步自动动作）？若只有一个 Error，它是否被同时当作两种语义使用——既允许自愈又号称终态？
- 终态（Done、Failed、Cancelled）之后是否仍可能执行工具或发起模型调用？迟到的事件（工具结果、审批回调、重复投递）能否把终态任务“复活”？

### 正向证据

- 状态转换表、运行时守卫及针对非法转换的测试一致。
- 工具结果先成为可追踪的真实状态，再供模型决策；最终完成有明确条件。
- 等待审批期间，即使模型再次生成调用意图，执行层也不会绕过审批。

### 典型缺陷与改进方向

- **只有 `while True` 和状态标签**：补充显式转换规则、终态门禁与非法事件处理。
- **把模型工具请求当成执行成功**：以工具真实结果和外部操作记录更新状态。
- **状态机替代权限系统**：状态机控制流程，执行层仍需独立授权与业务校验。

## 4. D3：状态、上下文与持久化（权重 10）

### 审查问题

- 状态是否超越聊天记录，包含任务 ID、工具记录、计划/子任务、执行进度、预算、错误、更新时间和必要版本信息？
- 上下文裁剪、摘要和结果引用是否保留关键事实？模型能否在需要时重新读取原始记录？
- 工具结果是否无上限塞入后续上下文？是否有大小、数量与敏感性约束？
- 长任务是否在关键节点保存 Checkpoint？存储是否考虑原子写入、并发更新、版本迁移、权限和敏感数据保护？持久化是否通过统一存储接口抽象，使 JSON 文件到数据库的替换不影响运行时核心逻辑？
- 恢复所需状态与提供给模型的上下文是否分离，避免把持久化记录简单等同于 Prompt 历史？

### 正向证据

- 状态结构能支持继续决策、停止判断、审计和恢复，且与消息协议有明确映射。
- 长任务使用带版本的持久化状态；多实例写入有并发控制，关键事实不依赖易丢失的摘要。
- 短期、无恢复需求的产品可将复杂持久化判为 NA 或低优先级，并说明理由。

### 典型缺陷与改进方向

- **只保存消息**：补充结构化执行状态与结果引用。
- **历史无限增长**：采用裁剪、摘要、外部结果引用和按需重读，并验证关键事实不丢失。
- **教学式 JSON 直接用于多实例生产**：增加原子性、锁/版本、迁移和访问控制；不要仅以“用了数据库”判定合格。

## 5. D4：工具治理、权限与副作用（权重 15）

### 审查问题

- 工具是否有统一的描述、参数、执行、结果与错误接口？注册表是否能拒绝重名和未知工具？分发器对未注册工具名是拒绝并给出受控错误，还是静默降级到其他工具（模型幻觉工具名会得到"看似成功"的正反馈）？
- 当工具面可扩展（MCP、插件、动态注册或配置化接入第三方服务）时，缺省安全值是什么：未显式配置白名单时是拒绝暴露还是全量暴露？授权绑定到具体工具与资源，还是配置了扩展点就等于授权其全部能力？写类/不可逆工具是否有别于只读工具的接入、白名单与确认路径？
- 每次执行前是否校验工具存在性、参数 Schema、取值范围、当前用户权限和业务规则？模型修正后的参数是否重新校验？
- 使用 ReAct 文本协议时，是否有严格解析、校验与错误处理？使用 Function Calling 时，是否仍完成执行、安全和恢复控制？
- 工具动作是否按风险采用不同控制？高风险写入是否有执行层授权、审批、幂等、事务/核对与审计？
- 审批是否绑定到具体动作要素：审批主体、被授权的工具与资源、规范化参数摘要、操作 ID、版本与有效期？审批通过后修改金额/资源/工具等实质要素时，旧审批是否失效并要求重新审批？模型或工具文本中的“已批准”是否不构成授权？
- 对“外部已成功、本地未收到结果”的未知结果，是否有查询状态、幂等重放、补偿或人工核对路径？其中：只有已证实端到端幂等才允许同操作重放；**补偿本身也是会产生副作用的动作**，必须独立授权、校验、幂等并审计；外部状态无法核对时，安全终态是“结果未知/转人工”，不得自动补齐成功或失败。
- 是否限制模型生成内容的直接执行，例如避免不受约束的 `eval`？对模型生成的表达式/代码类输入（计算、脚本片段），是否补充了长度、数值范围、除零与计算复杂度等资源边界，而不是直接交给通用解释器？工具返回和外部内容是否作为不可信数据处理？
- 日志与错误反馈是否避免泄露凭证、个人隐私和敏感参数？

### 正向证据

- 结构化协议与每次执行前的确定性校验并存，权限以当前主体和资源为依据。
- 高风险动作有稳定幂等键、外部操作记录、状态核对和可复现的重复副作用测试。
- 工具错误以受控、可关联的形式反馈；未知结果不会被描述为成功。

### 典型缺陷与改进方向

- **注册成功即认为可调用**：在执行前独立做授权与风险检查。
- **所有工具共用盲目重试**：按动作幂等性和结果确定性制定策略。
- **模型“猜测”外部动作结果**：标记结果未知并核对真实状态，必要时暂停并请求人工处理。

## 6. D5：停止、预算、超时与取消（权重 12）

### 审查问题

- 是否按任务类型配置最大步数，而非所有任务共用一个任意常数？达到上限后是否记录明确停止原因？
- 是否根据模型接口实际用量累计 Token，并在多模型场景考虑费用预算？
- 是否分别设置单次模型、单次工具和整个任务的超时？这些限制是否覆盖连接、读取和排队等阶段？
- 是否检测相同动作、相同结果、重复错误和长期无进展？判断是否考虑数据新鲜度和合理轮询？
- 自愈是否有独立上限，避免与步数、重试形成放大的乘积？
- 取消是否传递到模型、工具和调度器？评价时区分四个层级，不要合并成“取消是否有效”一个问题：
  1. 不再发起新调度（最低要求）；
  2. 尚未发出的写入被拦截；
  3. 在途调用按能力尽力取消（底层不支持时不作硬性要求）；
  4. 外部动作的真实结果被核对并如实报告（已发生的副作用不因取消而消失）。
- 取消后到达的迟到结果是否只用于对账记录，而不会把 Cancelled 改写成“成功完成”？取消与外部写入并发时是否有明确的先后判定点？
- 达到 Done、Failed、Cancelled 或预算上限后，是否仍可能发起新模型/工具调用？

### 正向证据

- 步数、Token/费用、时间、重复无进展和自愈次数形成多层边界，并有达到边界的测试。
- 每次停止都有机器可读原因和可观测事件；取消后的终态门禁经过验证。
- 合理轮询、动态数据查询不会因简单重复检测被误杀。

### 典型缺陷与改进方向

- **只限制步数**：补充实际 Token/费用与分层时间预算。
- **UI 显示取消即视为取消完成**：区分停止调度、取消底层操作和外部副作用已停止，分别验证。
- **相同参数一律禁止**：结合动作幂等性、数据时效和结果变化识别无进展。

## 7. D6：错误处理、自愈与恢复（权重 15）

### 审查问题

- 是否至少区分输入/参数错误、瞬时错误、不可恢复错误，以及外部结果未知？每类错误的负责层和处理策略是否明确？
- 参数错误是否以可理解校验结果反馈，并在有限修正后停止、降级或请求补充信息？
- 瞬时错误是否有限重试，采用指数退避和随机抖动；权限不足、取消、预算耗尽是否停止而非重试？
- 重试是否区分工具层重试与模型重新规划，避免多层重试叠加失控？
- 自愈后是否重新执行 Schema、权限和业务校验，并保留错误类型、工具、参数摘要、次数、修复结果和最终状态？
- Checkpoint 恢复是否先核对未决外部动作的真实状态？不支持幂等的系统是否有核对或补偿流程？
- 信息不足或部分工具失败时，最终答案是否明确不确定性和缺失证据，而非编造完整成功结果？

### 正向证据

- 错误分类与处理矩阵、实际故障测试和恢复后的外部操作记录一致。
- 对“成功但未保存结果”的崩溃点进行恢复测试，证明不会重复产生副作用。
- 系统可以安全失败：给出部分结果、明确缺口、请求澄清或转人工，而不是强行完成。

### 典型缺陷与改进方向

- **所有异常都交回模型“再想想”**：把不可恢复错误和高风险未知结果交由确定性策略处理。
- **保存 Checkpoint 后直接重放**：先核对操作 ID、幂等键与外部状态。
- **重试最终成功就删除错误历史**：保留完整恢复轨迹，用于定位模型、接口、业务规则和底层服务问题。

## 8. D7：规划、依赖与并行控制（权重 6）

### 审查问题

- 任务是否确实需要先规划或并行？简单动态任务使用 Plan-and-Execute 是否反而增加延迟与成本？
- 模型生成计划后，程序是否验证任务 ID、依赖存在性、循环依赖、工具许可和预算？
- 是否在新观察使原计划失效时重新评估或重规划，而不是盲目执行旧计划？
- 仅独立任务是否并行？是否有并发上限、结果关联、取消传播、部分失败与汇总策略？
- 如果没有规划或 DAG，该能力对当前产品是否确实不适用？

### 正向证据

- 计划由模型提出、程序验证，DAG 或依赖图用于明确可运行节点，而非仅作为展示。
- 并行缩短可证明的关键路径，且不会放大外部服务压力、预算或副作用风险。

### 典型缺陷与改进方向

- **把计划文本当成合法执行图**：增加确定性计划校验。
- **为追求高级架构强行引入 DAG**：按任务复杂度选择 ReAct、Plan-and-Execute 或两者结合。

### 多智能体产品（按能力启用）

仅当产品确实使用嵌套/子代理/多智能体编排时检查以下项；单体 Agent 不适用，不因缺少这些机制扣分：

- 父子代理是否共享同一全局预算与截止时间？子代理的步数/Token 是否会乘出放大的总量，或各自独立限额而绕过总上限？
- 取消是否向所有子代理传播？某个子代理失控时能否单独终止而不阻塞整体？
- 权限委派是否可能放大？子代理获得的工具权限是否不超过其任务所需（最小权限），用户授权是否可被代理链稀释？
- 操作 ID 与 Trace 是否贯穿父子代理，外部副作用能否追溯到最终发起的代理？
- 是否限制递归生成代理的深度与数量，防止自我繁殖失控？

## 9. D8：可观测性、审计与证据链（权重 10）

### 审查问题

- 是否有任务开始、模型调用、工具调用/结果、状态转换、错误、预算和完成事件？事件是否能通过任务与调用标识串联？是否包含答案增量类流式事件，而不是只等最终结果？
- 事件是否通过统一异步接口逐条输出（如异步生成器、消息流，经 SSE 或 WebSocket 送达前端），使运行时核心逻辑不依赖某一 UI 框架？
- Trace 能否回答模型调用次数、最慢工具、常见错误、停止原因、预算去向和最终答案依据？
- 面向用户的进度事件与内部调试日志是否分离？是否脱敏并控制访问？
- 最终答案是否能关联真实工具结果或原始凭证？工具失败时是否仍生成无依据的确定结论？
- 是否度量任务成功率、执行时长、单位成本、错误恢复效果和重复副作用，而不只评估答案外观？
- 是否区分**执行状态**（循环是否正常结束）与**结果状态**（业务目标是否完成、部分完成或未知）？“任务跑完”不等于“目标达成”，部分完成不得显示为完全成功。
- Trace 除自身完整外，是否可与独立事实源（模型网关计数、工具执行记录、外部业务台账）对账？防止“完整但不真实”的自洽 Trace。
- 是否避免把隐藏思维链当作审计前提？应以可观察行为、工具记录、状态与结果证据审查。

### 正向证据

- 从最终结论可追溯到具体工具结果、状态和操作记录；用户事件不泄露敏感细节。
- 指标按任务类型和版本持续统计，故障恢复也能被量化。

### 典型缺陷与改进方向

- **只有最终答案日志**：补充统一事件流和端到端 Trace。
- **页面显示“已查询”就认定证据充分**：核对真实工具结果与答案引用的一致性。

## 10. D9：测试、评估与发布保障（权重 12）

### 审查问题

- 是否通过模拟模型响应和工具结果测试执行循环，再在测试环境用真实模型做集成评估？
- 是否同时检查最终答案和中间过程，防止“答案看似合理但没有真实查询”？
- 测试是否覆盖普通回答、正常工具、非法工具、参数错误、超时、重复无进展、预算、取消、恢复、权限和重复副作用？
- 是否测试关键崩溃点、外部结果未知、审批绕过、终态后调用和敏感日志，而不只测试快乐路径？
- 随机性是否通过多次运行和代表性任务集评估？是否有成功率、成本、延迟和恢复质量的发布门槛？
- 测试证据是否对应当前版本，模型、Prompt、工具和策略变化后是否回归？

### 正向证据

- 正常与故障路径都有可重复测试；关键门禁有明确通过标准和最近一次执行结果。
- 评估既衡量答案质量，也衡量过程真实性、资源消耗和外部副作用。

### 典型缺陷与改进方向

- **Demo 成功截图作为生产证据**：建立自动化单元、集成、故障注入与发布门禁。
- **只检查最终文本**：将工具调用、状态转换、真实凭证和外部系统记录纳入断言。

## 11. 防止过度审查

- ReAct 并非天然不合理；关键在解析、校验和错误处理。Function Calling 也不会自动带来安全与恢复能力。
- 状态不是越多越好，框架不是越复杂越好；有清晰转换守卫比使用某个状态机库更重要。
- 重复调用可能是合理轮询，重试对只读幂等操作可能合理；应结合语义和结果判断。
- 短任务未必需要持久化，简单任务未必需要规划、DAG、并行、多智能体或长期记忆。
- 未看到内部实现时标记 NE 并提出取证/验证建议，不写成“确认没有实现”。
- 设计成熟、证据充分的产品应明确肯定；不要为了制造问题而提出高成本、低收益的改造。
