# Token 经济性审查基线（成本视角）

本基线把《Agent 降本实战：Token 账单砍掉 90% 的六板斧》（玄姐聊AGI，2026-10）中的降本实践转化为审查问题。原文链接：https://mp.weixin.qq.com/s/DE2jOTHMnsYhu_F1Buob2A

**定位**：Token 成本是工程架构质量的一个侧面——结构性浪费几乎总与架构错配同源。本文件不新增独立评分维度，而是作为 D1（架构适配）、D3（状态与上下文）、D4（工具治理）、D5（预算与停止）、D7（多智能体）、D8（可观测性）的成本视角深化材料：其中的检查项并入对应维度评分，不重复计分。用户明确要求"审查 Token 成本 / 账单 / 性价比"时，也可用本文件单独做专项快评（快速档）。

**核心判断**：Token 优化的本质是资源精准配置——该花的地方一分不省（关键推理环节保留旗舰模型），该省的地方一分不花（确定性环节外移到工程）。架构判断一句话：**确定性交给工程，不确定性交给模型**。

**证据纪律**：本文件引用的单价倍数、折扣比例与厂商规则（如缓存命中 10%、写入溢价 25%、高峰 2 倍价）均为文章发表时的业界参考值，各厂商规则差异大且随时间变化。审查时以被审产品实际使用的模型当前定价与真实 usage 数据为准，不要把参考值当成常数套用。

## 1. 先看度量：没有成本画像就没有成本审查

优化的前提是知道钱花在哪。审查任何成本问题前，先确认被审产品有没有成本画像。

**计费由四类 Token 构成**，审查问题围绕"能否区分并度量它们"：

| Token 类型 | 构成 | 价格关系（参考） |
|---|---|---|
| 输入 Token | 系统提示词、工具描述、历史对话、用户消息 | 基准价 |
| 输出 Token | 模型生成内容，含推理过程 | 通常为输入的 3–6 倍，**无法缓存** |
| 缓存命中 Token | 命中 Prompt 缓存的输入部分 | 可低至输入价的 10%–20% |
| 缓存创建 Token | 首次写入缓存的部分 | 与输入持平，部分厂商有溢价（如 125%） |

**审查问题**

- 是否按调用记录模型、输入 / 输出 / 缓存命中 / 缓存创建四类 Token 用量与成本，并按功能模块归集？
- 能否回答"钱花在哪个环节、哪个环节涨得最快"？
- 缓存命中率是否作为核心指标持续监控？多模型场景是否分别统计？
- 计费模型是否按真实命中率核算，而不是只按官网标价估算？（厂商间自动缓存 / 显式缓存、有效期、分时计价差异大）

**正向证据**：网关或平台的 usage 日志可查四类 Token 明细，成本可按模块归集，缓存命中率有监控与告警。

**典型缺陷**：只记录调用次数或 Token 总数，无法区分输入输出与缓存命中——成本问题既无法定位也无法验证改进效果。此时第一优先级建议是补监控，而不是直接给优化清单。

## 2. 前缀稳定性与缓存命中：输入侧最大的可控杠杆

Prompt 缓存采用**前缀匹配**：只有本次请求的前 N 个 Token 与历史请求逐字节一致才命中，从第一个不一致的 Token 起全部按原价计费。因此消息组装顺序本身就是架构设计。

**正确顺序**：System Prompt（固定）→ 工具描述（固定）→ 历史对话（半固定，只追加）→ 用户消息（变化）。把变化内容前置（如用户数据放最前）会使几千 Token 的固定内容全部无法命中。

**破缓存元凶清单**（逐项排查）：

1. System Prompt 拼接当前时间戳、请求 ID、用户名等每次变化的内容；
2. 工具列表顺序不稳定，或按用户权限动态增删导致序列变化；
3. JSON 序列化字段顺序不稳定（应固定 Schema 字段顺序或显式排序）；
4. 中途修改 / 重写历史消息，而不是只在末尾追加。

**审查问题**

- Prompt 组装顺序是什么？固定内容是否全部前置、变化内容是否后置？
- 历史对话是否只在末尾追加？有无每轮改写历史的机制？
- 序列化是否确定（字段顺序稳定）？
- 与上下文管理的联动：裁剪 / 摘要 / 编辑历史的频率是否破坏前缀（见第 4 节冲突项）？

**正向证据**：组装顺序固定→半固定→变化；连续多轮任务的缓存命中 Token 占比可达 70%–90%（参考值）；有前缀稳定性测试。

**典型缺陷**：动态内容前置或每轮重写历史导致缓存系统性失效；修复仅需重排组装顺序，属低成本高收益项。

**验收标准示例**：同一多轮任务原样重放，第二轮起缓存命中 Token 占输入 Token 的比例 ≥ 目标值；在 System Prompt 注入一个每次变化的前缀字段后该比例显著下降，可证实破坏点位置（对应 T-23）。

## 3. 模型分层与选型匹配：性价比最高的架构决策

**审查问题**

- 各环节的模型档位是否与任务复杂度匹配？流程化调度环节（读取数据、识别类型、分发任务、汇总结果）是否用了旗舰模型？核心推理环节是否反而被降档？
- 多智能体场景：主 Agent 与子 Agent 是否分档（主用低成本、子用旗舰），还是无差别同档？
- 路由方式是哪种：静态路由（按角色写死）、规则路由（按任务类型 / 输入长度 / 关键词分流）、级联路由（小模型先答、置信度不足再升级）？级联路由是否有可信的升级判据？
- 预算阈值触发的降档是否仍以任务风险和质量门槛为约束？高风险或关键推理任务不能因费用耗尽自动绕过质量门禁；安全做法是停止、降级能力、排队或转人工，而非无条件切最低档。
- 切换模型是否重新校准上下文窗口、压缩阈值、检索块与历史预算，并验证分词/成本、工具调用和结构化输出协议兼容性？模型切换后的质量回归是否覆盖路由前后的代表性任务？
- 语言与分词匹配：以中文为主的任务是否按中文理解/生成质量、分词效率和实际单价实测选型，而不是仅看通用榜单或默认“中文原生”？同等信息量下不同分词器的 Token 消耗可差 30%–50%（参考值），叠加单价差异总成本可差数倍。

**正向证据**：有按环节的模型选型依据；调度与推理分档；目标语言任务的质量与分词/成本结论有实测数据支撑。

**典型缺陷**：**旗舰模型做流程调度**——既是成本错配（调用量大的环节单价最高）也是可靠性误判（结构化调度交给 LLM 反而更不稳定）；应下沉为脚本 / Workflow 或换用低档模型。反向缺陷同样存在：为省钱把关键推理降档，牺牲任务质量。

**成本影响估算方法**：某档环节调用量占比 × 两档价差 ≈ 该项优化对总成本的影响。例如调度占 60% 调用量、两档价差 5 倍时，仅此一项总成本约降一半（参考值）。报告中的量化表述应给出计算依据，不凭空报数。

## 4. 上下文供给方式：全量注入是最大的 Token 黑洞

审查"模型每一轮到底看到哪些 Token"。四种高发浪费形态：

1. **全量读取大文档 / 记忆**：知识库、MEMORY 类文件每轮全量注入，而真正相关的只有几十字。改进：检索增强（关键词 + 向量 + 重排融合，只注入 Top-K 片段），并保留按需重读原始记录的能力（与 D3 关键事实保留检查联动）。
2. **工具定义全量注入**：工具一多，描述每轮重复发送、吃掉数万 Token。改进：常用工具常驻并保持顺序稳定（吃缓存），长尾工具做目录 + 按需检索加载。**适用门槛**：工具定义超过约 1 万 Token（参考值）或模型经常选错工具时才值得上；五六个工具的小库不必折腾（防过度设计）。
3. **中间结果在上下文中流转**：大表、长列表经工具返回后在对话里来回过滤，Token 随轮数放大。改进：代码执行模式——模型写代码调用工具，数据留在执行环境内过滤，只回传最终结论（参考降幅可达 90% 以上）。**代价前置**：需要沙箱、网络白名单、资源限额与审计，安全永远排在省钱前面（与 D4 代码类输入资源边界检查联动）。
4. **长程历史无限增长**：上百轮后每轮为过期信息重复付费，且上下文过长本身影响稳定性。改进（三选一或组合）：上下文编辑（自动清理陈旧工具结果）、压缩摘要（Compaction，注意别压丢关键事实）、子 Agent 隔离（检索、探索类"脏活"在独立上下文跑完，只回传精炼结论）。

**与缓存的冲突（容易误判的精妙点）**：上下文编辑与压缩会改动前缀，导致缓存失效——每轮都压缩可能让总成本不降反升。正确做法是**低频、批量**进行（如攒到一定长度整体压缩一次），而不是每轮微调。

**审查问题**

- 记忆 / 知识库 / 工具定义 / 历史四类内容各以什么方式进入上下文：全量还是按需？
- 工具返回的大结果有没有大小约束与过滤层？
- 裁剪与压缩的触发频率是多少？是否与缓存前缀稳定性冲突？
- 子 Agent 的上下文隔离是否真的只回传结论，还是把原始结果又倒回主上下文？

**正向证据**：上下文构成有预算意识——固定内容稳定前置、大文档检索注入、大结果在执行环境过滤、历史低频批量压缩，且有关键事实不丢失的验证。

**验收标准示例**：单任务平均输入 Token（不含缓存命中折算）较改造前下降 ≥ 目标值；检索注入后对早期关键事实的问答仍可追溯原始凭证（联动 T-15）。

## 5. 输出控制：最贵且无法缓存的一侧

输出 Token 单价通常为输入的 3–6 倍且无法缓存，只能从源头控制长度。

**审查问题**

- 是否设置 max_tokens？是否使用结构化输出（JSON Schema）约束格式与长度？
- 能否只输出差异 / 结论而非全文复述（如报告只输出变更段）？
- 排版、格式化类输出是否本可以脚本生成，而非让模型逐字生成全文？

**正向证据**：输出有长度边界与结构约束；长报告采用"模型出结论 + 程序排版"的分工。

**典型缺陷**：无 max_tokens 上限（与 D5 预算检查联动）；每次全文重生成不变部分。

## 6. 确定性外移：脚本优先与 Workflow 化（架构级手段）

这是第 3 节"模型分层"的彻底形态，与 D1 架构适配直接同源。

**判断标准**：if-else 和正则能搞定的事，不交给 LLM。LLM 只做理解、推理、生成三件事。典型可外移环节：数据获取与格式化、定时检查、参数预校验、报告排版。

**收益是双维度**：成本（外移环节 Token 降为 0）+ 可靠性（结构化操作由脚本执行更稳定、更快）。审查时不要只算成本账——某环节"用 LLM 读数据有约 15% 失败率"这类问题与成本问题同根同源。

**Workflow 替代流程化调度**：当主 Agent 的行为完全流程化（读数据 → 识别类型 → 分发 → 汇总），可用确定性 Workflow 完整替代，调度环节零 LLM 调用；模型只出现在真正需要动态判断的子环节。

**防误判**：动态决策环节不能强行 Workflow 化——按任务路径的实际复杂度判断（回到 D1 的适配判断），不要见到 LLM 调度就建议外移。

## 7. 错峰、批处理与极致手段（P2 建议素材）

以下手段只在条件匹配时提出，否则记 NA，不要作为缺陷：

- **错峰调度**：所用模型分时计价（如高峰 2 倍价）且任务非实时（报表、离线评测、数据标注）时，排闲时执行。
- **批处理接口**：离线场景可用批量折扣接口，代价是结果非实时返回。
- **自托管、量化、推测解码**：用量大到一定规模后才值得评估，中小用量直接提反而增加负担。

## 8. 发现分级与 ROI 改进路线

**严重度映射**（对齐基线 1.3，不另设标准）：

| 情况 | 严重度参考 |
|---|---|
| 无成本度量 + 无预算边界 + 高用量场景（成本失控不可见也不可停） | 高（联动 D5 与门禁 3 判断） |
| 结构性浪费：系统性破缓存、全量注入大文档 / 工具定义、旗舰模型做调度、大表在上下文流转 | 中（成本与可维护性不足，应优先改进） |
| 局部优化项：错峰、批处理、未设 max_tokens（无失控风险时） | 低 / P2 |

**改进建议按 ROI 排序**（作为第 7 节改进路线中成本类条目的排序依据）：

1. 补监控：四类 Token 用量 + 按模块归集 + 缓存命中率（没有度量先做这个）；
2. 前缀稳定 + max_tokens + 结构化输出（低成本改动，通常先拿下大头）；
3. 模型分层路由 + 语言匹配（性价比最高的结构性调整）；
4. 架构改造：脚本优先 + Workflow 化 + 检索增强（按业务场景选做）；
5. 上下文工程：工具按需加载 + 代码执行模式 + 低频压缩（适合工具多、链路长的复杂 Agent）；
6. 极致优化：错峰、批处理、自托管、量化（量大再考虑）。

每条成本类建议的验收标准应可复测且用成本指标表达，例如："同一任务集重放，缓存命中 Token 占比从 X% 升至 Y%，单任务平均成本下降 Z%"——不接受"优化 Prompt、控制成本"式不可测表述。

## 9. 按证据模式的取证边界

- **黑盒**：账单、价格页、响应延迟可观察；Prompt 组装顺序、模型路由、缓存配置通常未知 → 记 NE，建议供应商提供 usage 明细，不臆断内部浪费。
- **灰盒**：设计文档 / 配置中的消息组装顺序、模型选型、工具清单规模、缓存与压缩策略是主要证据（中等强度，需行为验证）。
- **白盒**：代码中的 Prompt 组装、序列化方式、缓存控制、压缩触发策略、usage 记录为强证据。可用零成本探针：固定输入连续调用两次，对比 usage 中缓存命中字段的变化，不产生业务副作用即可证实或排除前缀稳定性问题。
- **运行工件**：网关 / 平台 usage 日志是最强成本证据，可与 D8 的独立事实源对账方法联动——自报"缓存命中率 80%"要与网关计数核对。

## 10. 常见误判（防止过度审查）

- **Prompt 长不等于浪费**：有前缀缓存时，长而稳定的 Prompt 可能比短而每轮变化的更便宜。不要仅凭长度建议压缩；关键词是"稳定"，不是"压缩"。
- **每轮裁剪 / 摘要不等于优化**：可能既破坏缓存前缀又丢关键事实。低频、批量的压缩才是正解。
- **没上 Tool Search / RAG 不等于缺陷**：小工具库、小文档集上这些机制是过度设计；先看规模门槛。
- **用了旗舰模型不等于浪费**：关键推理环节保旗舰是正确配置；审查的是档位与任务复杂度的**错配**，不是"有没有用最便宜的模型"。
- **不是所有 Agent 都有成本问题**：低频、低用量、内部工具型产品，Token 成本可能全部为 P2 甚至 NA；审查深度与用量和业务影响成正比。
