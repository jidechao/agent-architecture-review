# MeetingPilot 会议跟进桌面 Agent 生产设计摘要

## 业务与运行形态

MeetingPilot 以桌面常驻进程运行。会议平台通过 Webhook 投递“会议结束”事件，Agent 解析纪要、读取相关文档、创建待办并通知负责人，最后把报告写入企业云盘。消息队列为至少一次投递，消费者重启或响应超时时，平台会再次投递同一事件。

## 事件接入与身份

1. Webhook 接收端只校验 URL 中配置的固定 token，不校验平台签名和事件时间戳。`event_id` 会写入日志，但每次投递都会生成新的 `run_id` 并直接启动新任务；没有事件去重表或业务操作 ID 映射。
2. 文档、任务、IM 和云盘工具统一使用一个权限较大的 MeetingPilot 服务账号。MCP Server 只验证该服务账号，不接收最终用户身份，也不按具体用户和资源重新授权。设计说明要求模型“不要读取用户无权查看的内容”。定时系统任务同样使用该账号。
3. 创建待办和发送通知使用 `run_id + 步骤名` 作为幂等键。同一事件的重复投递因为生成了新 `run_id`，会得到不同幂等键。

## 编排、重试与恢复

4. Orchestrator 使用显式状态机，Checkpoint 包含状态版本、步骤、工具调用 ID 和结果引用；通知通过事务 outbox 发送。恢复外部写入前先按操作 ID 查询状态，已确认成功的动作不会重放。
5. 工具层对 429 和 5xx 最多重试三次，遵循 `Retry-After`，使用带抖动的有界指数退避；401/403 不重试。队列等待长度、每用户并发数和下游请求速率没有上限。所有任务共享同一个文档服务连接池；没有熔断、舱壁隔离或降级策略，下游变慢时工作线程和重试请求会继续累积。
6. 桌面看门狗发现主进程无响应后直接终止并重启。重启后扫描 `Running` 任务并恢复，但未定义旧进程与新进程的 fencing/租约，也不处理仍在运行的工具子进程。没有内存、句柄、CPU、子进程数量或连续重启次数限制，也未测试操作系统休眠/唤醒。界面显示“运行中”即被当作服务健康证据。

## 审计与模型路由

7. 审计使用 JSONL，按天轮转、单文件 100MB、保留 180 天，记录时间戳、工具名、完整参数、执行结果和耗时。MeetingPilot 进程与运维人员共用可改写审计目录的账号；只记录成功调用，不记录被拒绝的访问。记录中没有最终用户、代谁执行、关联审批/策略来源和原始事件 ID。工具参数中的访问令牌也会原样写入。
8. 模型默认走中档，质量评分不足时升级旗舰模型，但尚未定义质量评分验证集。部门费用超过预算后，所有任务（包括合规判断）都自动切换到最低档模型。手动切换模型只更换 API 配置，仍沿用原模型的上下文窗口、压缩阈值和工具协议假设；没有切换后的回归评估。

## 试点数据与测试

9. 两周试点覆盖 30 名员工。系统任务终态完成率为 92%，纪要初稿生成时间从人工约 30 分钟降至 5 分钟，因此项目材料宣称“效率提升 6 倍、ROI 已证实”。另有 38% 的初稿需要人工大幅修改，但修改时间未计入；未统计持续使用率、人工复核成本、模型与 MCP 运维成本及开发投入。
10. 已有测试覆盖正常会议流程、工具超时后的有限重试、Checkpoint 版本迁移，以及外部成功但本地保存失败后的恢复。尚未测试 Webhook 伪造/重放、重复投递、队列积压、下游长时间 degraded、连续崩溃重启、休眠唤醒、审计篡改和模型降级后的任务质量。本摘要不包含这些未执行测试的结果。
