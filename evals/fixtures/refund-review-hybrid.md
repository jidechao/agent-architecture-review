# RefundLens 退款异常分析系统设计摘要

## 业务与架构

RefundLens 用于电商售后：先按固定规则完成退款资格审核，再对异常订单生成原因分析。资格审核、退款写入和通知发送均由确定性 Workflow 执行；只有异常原因归纳使用 Agent，因为查询路径会随日志和订单结果变化。Agent 默认只能使用只读工具。

## 已提供的设计与测试证据

1. 运行时明确区分决策器、工具执行器、状态存储和事件总线。模型只产生工具调用意图，执行器负责工具查找、JSON Schema 校验、权限检查和结果关联。
2. 状态机包括 `Thinking`、`Acting`、`WaitingApproval`、`Paused`、`Cancelled`、`Done`、`Error`。文档给出转换表；Done/Cancelled 为终态，WaitingApproval 只能由带有效审批 ID 的事件推进。
3. 退款写入不经过 Agent 自由决策。Workflow 在执行层重新校验用户权限、业务规则和审批记录；审批不是 Prompt 条件。
4. 所有写入使用稳定业务幂等键。执行器采用“先查询操作状态，再决定是否重放”的恢复策略，并以事务 outbox 发送通知。
5. 步数、模型 Token、费用和任务总期限按任务类型配置；模型与工具分别有连接和读取超时。重复动作签名结合结果指纹与数据新鲜度判断，不直接禁止所有重复查询。
6. 取消通过协作式取消令牌传递到工具；对不支持取消的数据库驱动，文档明确标注“只停止调度，不保证底层立即停止”，并对后续写入设置终态门禁。
7. 错误分为参数错误、瞬时错误、权限/取消/预算等不可恢复错误。仅瞬时错误由工具层执行有限指数退避和抖动；参数修正最多两次，权限错误不重试。
8. Checkpoint 记录计划、子任务、工具调用 ID、结果引用、预算和状态版本。多实例更新使用乐观锁；状态快照原子写入，敏感字段加密。
9. 长上下文采用摘要加结果引用，关键业务事实保存在结构化状态；摘要后必须重新读取原始凭证才能生成最终分析。
10. Trace 关联模型调用、工具调用、状态转换和最终答案引用。面向用户的进度事件不包含内部参数，开发日志默认脱敏。
11. 测试证据包括：正常只读分析、非法工具名、Schema 错误、模型超时、工具超时、重复无进展、取消、进程崩溃恢复、审批绕过、重复退款、Trace 脱敏和最终答案凭证一致性。
12. 最近一次故障测试结果：100 次“工具已执行成功但结果保存前崩溃”的恢复测试中，重复退款为 0；50 次取消后的写入门禁测试均通过。
